## Installed Host startup/throughput recheck

`NDM_QA_HOST_PATH=/Applications/NDM.app/Contents/Resources/bin/NDMHost node scripts/qa-startup-throughput-audit.mjs --expect-fixed`
passed against the installed Host hash in the deployment receipt, using isolated
support/ports and a separate headless Chrome profile. Owned fixture state was
cleaned by the harness. All downloaded bytes were compared with the synthetic
8 MiB payload.

| Controlled scenario | First server body | First RPC-reported progress | Completion |
| --- | ---: | ---: | ---: |
| Strong identity, one connection | 41 ms | 117 ms | 4,064 ms |
| Strong identity, eight connections | 35 ms | 56 ms | 652 ms |
| No validator, safety single stream | 36 ms | 109 ms | 4,076 ms |
| Delayed HEAD, eight connections | 35 ms | 56 ms | 650 ms |
| Chrome download, same delayed-HEAD fixture | 35 ms | not measured | 4,058 ms |

The NDM paths issue GET without waiting for HEAD. The fixture intentionally caps
each response to 64 KiB per 30 ms, so parallel connections gain artificial local
bandwidth. These are neither general Internet speed claims nor Electron visible
paint timings. Chrome is a real headless download using an isolated profile.
[Raw report](core-audit-2026-10-04/installed-2026100505-startup-throughput.json).

The original audit's connection-explanation gap remains: native fallback for a
missing strong representation validator is logged, but its reason is not exposed
to the Electron inspector. Active request count/request limit are exposed. This
should not be mistaken for a missing multi-connection implementation.
