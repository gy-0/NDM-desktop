# 完成文件移动后的恢复审查

日期：2026-09-12。范围：当前源码与既有测试的只读审查。没有移动、选择或扫描用户文件，没有运行应用、构建或新增产品代码。下文的恢复流程是提案，尚未实现或通过真实平台验收。

## 结论

NDM 目前保存的是文件原路径。用户在访达或资源管理器中移动、重命名完成文件后，没有重新关联入口；预览、打开和拖出也没有完整的恢复闭环。有些失败甚至被报告为成功：文件已不存在时，“在访达中显示”会退而打开原文件夹。

建议只做一项功能：**在确认文件缺失时提供“找到文件…”**。用户选回已有文件后，原任务立即恢复打开、预览、显示位置和拖出。正常任务不新增常驻按钮，主列表不加一列，也不出现挡住内容的持久错误横幅。

这应当是“恢复使用已有文件”，而不是修改下载目录。不能直接覆盖 `folderPath` / `filename`：目前它们同时参与重新下载、删除及临时产物清理；把外部选来的文件塞进同一位置，会意外扩大这些操作的作用范围。

## 当前行为与缺口

| 入口 | 当前代码实际行为 | 对用户的影响 |
| --- | --- | --- |
| 空格、快捷命令、列表文件操作 | 根据任务的 `folderPath + filename` 发起操作。空格预览另有一条并行处理路径。 | 原路径失效后只能重试同一路径，没有找回途径。 |
| 详情中的文件卡片 | 同样使用原路径；局部提示约 3 秒自动消失，切换文件会清空。 | 已避免持久错误遮挡，但提示没有下一步动作。 |
| 在访达中显示 | 文件存在则显示；缺失时先尝试安装收据中的应用，再打开原父目录并返回成功。 | 用户看到旧文件夹，却没有被告知下载文件不在那里；父目录打开结果也没有被等待确认。 |
| 快速预览 | 主进程返回布尔值。renderer 将 `false` 统一解释为“找不到文件，无法预览”。Windows 路径存在时忽略 `shell.openPath` 的错误字符串并返回成功。 | 缺失、权限、系统预览未能打开不能准确区分。不能看到 `false` 就引导重新关联。 |
| 拖出文件 | renderer 提交完成项路径数组；主进程同步检查，任意一项缺失就拒绝整组。事件只返回错误文案。 | 多选拖出时不知道缺的是哪一项，也无法把恢复动作准确绑定到任务。 |
| 保存位置 | 详情显示、复制位置，或打开目录。目录选择器只选目录；引擎的 `confirmDestination` 只确认尚未开始的下载。 | 现有“更改保存位置”不是完成文件关联功能，不能复用它的业务语义。 |

## 身份能力：已有的是什么，缺少什么

**macOS 原生引擎没有完成文件重新关联 API，也没有覆盖所有下载方式的长期文件身份记录。** [DownloadTask.swift](../../native/Sources/NDMCore/Models/DownloadTask.swift) 的最终地址仍是目录和文件名。

[OffsetDownloadStorage.swift](../../native/Sources/NDMEngine/OffsetDownloadStorage.swift) 的 `Identity` 使用设备号和 inode；检查父目录身份、常规文件类型、文件身份、大小及已落盘范围。这是保护下载中间文件与发布后清理的所有权凭证。它只在原父目录内检查凭证记录的名称，不查找文件系统中的新位置。`renamePublished` 执行同目录内的排他重命名，不是重新关联已经移动的文件。完成后，[DownloadManager.swift](../../native/Sources/NDMEngine/DownloadManager.swift) 的 `reclaimCompletedArtifacts` 可以验证并退役这份凭证。因此不能把它当成所有历史任务都有的“找回原文件”能力，也不能为了关联修改或重建这份清理凭证。

原生 `validatedRemovalURL` 防止路径穿越、目录与符号链接逃逸；它不是对历史下载内容的身份认证。`confirmDestinationUnlocked` 则要求 `awaitingDestination`、暂停且尚无工作数据，属于创建前的目录确认。

**Windows 同样没有现成的重新关联或持久文件身份 API。** [windowsEngine.ts](../../src/main/windows/windowsEngine.ts) 存储目录、文件名和大小；`safeTaskFile` 做路径范围检查，`restart` / `removeTaskArtifacts` 根据原名称处理最终文件及 `.aria2`、`.part`、`.ytdl`。目前没有原文件哈希或可直接复用的 Windows 文件 ID 合约。不能将 Node 的路径存在或大小相同当作身份相同，也不能未经 Windows 实测就把 POSIX inode 方案称作跨平台验证。

安装收据也须单独处理：[主进程 index.ts](../../src/main/index.ts) 按安装包源路径的哈希索引已安装应用。它证明的是某次安装的来源关系，不证明当前某个 DMG 是原文件。安装包移到废纸篓后仍可“打开应用”，不应误报整个任务不可用或要求找回安装包。

## 一项建议：缺失文件的“找到文件…”

### 交互闭环

1. 用户打开、预览、显示位置或拖出时，先获得结构化的文件状态。只有原文件明确不存在才出现：**“文件不在原位置” · 找到文件…**。不要断言“已移动”，因为删除、断开外置卷、权限问题可能表现相近。
2. 提示不挤动列表，不自动打开详情，不主动弹文件选择器。含动作的轻提示应可点击、可键盘到达，并在指针停留或获得焦点时暂停消失；不能继续沿用当前 `pointer-events-none`。原有“保存位置”区域也可以在已知缺失时用“找到文件…”替换失效的显示位置动作，让提示消失后仍有入口。正常状态完全不增加一排控件。
3. 点击后打开系统的单文件选择器，标题“找到「原文件名」”，确认按钮“关联文件”。以仍存在的原目录作为初始位置；该目录不可用时采用系统默认位置。选择器不自动搜索全盘，不访问其他目录来猜文件。
4. 用户选择后，只验证并保存这项文件关联，不下载、不复制、不移动、不上传文件。不更改任务 ID、下载来源、完成时间或创建收据。
5. 关联成功，原位置区域自然换成新位置；文件卡片刷新缩略图。用一次简短“文件已关联”反馈，不庆祝、不弹第二层完成窗口。若来自打开或预览，且任务和操作上下文仍一致，可以继续刚才的动作；拖拽会话已结束时不自动重发拖拽，用户再次拖出即可。

对于 `permissionDenied`、不可用卷或 `previewUnavailable`，分别给出匹配的短提示，不出现错误的“找到文件…”主行动。无法可靠分类时保留一般失败提示，不能推测成缺失。用户主动选别的位置仍可放在位置区域的次级操作中，但不是本轮默认恢复行为。

### 第一版对“原文件”的诚实边界

第一版采用**用户明确选择并关联**，不声称自动认出了原文件。历史记录大多没有完成时的内容指纹，同名、同扩展名、同大小都不足以证明同一内容。

- 候选必须是可读常规文件；目录、设备、符号链接及失效路径不接受。检测与持久化前都验证候选，避免选择后被替换。
- 有可信的最终大小时，以大小不同作为明显选错的提示；网络声明大小不等于可信最终大小。不能未经核对就用历史 `fileSize` 一律拒绝。大小未知或没有原身份的记录仍可由用户明确关联，记录来源为 `userSelected`。
- 新关联保存当前候选的身份与元信息，供**之后**识别路径上的替换；这不倒推证明它是原下载。不同卷上的拷贝也可以手动关联，不应因为 inode 不同就误判用户选错。
- 自动找回、完成时长期身份采集、跨卷内容哈希比对是后续独立能力，不是第一版的前置条件。首版不对几千条历史记录启动哈希任务或目录扫描。

### 关联与下载所有权分开

建议增加独立的“可使用文件引用”，不直接把用户选中的路径写回下载目的地：

```text
TaskArtifactReference
  taskID
  revision
  path
  displayName
  provenance: userSelected
  identity: 平台能够可靠提供的文件身份 + 选择时元信息
  associatedAt
```

这是供打开、预览、分享、显示位置、复制位置和拖出使用的引用。列表仍保留下载记录的原始名称；详情在“保存位置”中显示所选文件的实际名称，重命名后的差异不会被隐藏。原始下载目的地继续用于重新下载，二者不要在各组件内临时拼接混用。

必要生命周期规则：

- 新关联不授予下载引擎删除候选或清理其同名旁侧文件的权利。第一版删除此类任务只移除记录与关联；若后来支持将关联文件移到废纸篓，应明确作用于这份当前文件，并重新核验身份，不能继承旧目录的清理逻辑。
- 重试/重新下载开始时，旧引用退出当前产物位置，但不删外部文件。新的下载完成后使用新产物。清理 `.part` / `.aria2` / segments 等仍只按原有所有权规则。
- 同一任务关联与删除、重新下载须串行化；任务已删除或已离开完成态时拒绝提交。不得为了成功而重新创建任务。
- 只关联主文件，不按名称猜测、搬迁或重新绑定字幕、转录等附属产物。缺失的附属文件仍保留自己的状态。
- 将安装包关联与已安装应用的打开语义分开。源路径变化需要明确处理路径键索引的安装收据展示，不能无条件复制“已安装”身份给新候选。

## 实现切点与最小新增契约

| 可复用部分 | 用法与限制 |
| --- | --- |
| App 的 `runFileCommand`、`previewRequest`；文件卡片的 `generation` | 统一所有文件命令和空格分支；异步返回只更新原任务。取消或切换任务后不自动打开另一个文件。 |
| 文件卡片、详情的“保存位置” | 放恢复入口和关联成功后的实际位置；不新增常驻工具条。 |
| Electron 系统选择器、`shell` 文件操作 | 新增选文件方式，维持系统交互；不要将 `selectFolder` 改成双重语义。 |
| Native 任务锁、`DownloadStore` 事务 | 在生命周期锁内验证完成态、引用版本并原子写关联，失败不改变原任务。 |
| Windows `withTaskOperation`、原子状态写入队列 | 同样先持久化成功再发布新引用；旧轮询/保存不可覆盖新关联。 |
| 当前拖拽同步校验 | 继续同步启动真实拖拽；提前解析引用并缓存，不在 `dragstart` 内等待 RPC、文件选择或网络卷探测。 |

最小需要新增或调整的合约：

1. **任务文件解析/状态**：按 `taskID` 返回 `artifactRevision`、实际路径、显示名、引用来源和 `available | missingFile | unavailableLocation | permissionDenied | replacedFile | unknownFailure`。存在性用能保留错误原因的文件检查，不以 `existsSync === false` 统一分类。选中任务或实际操作时检查，避免每次刷新对整个下载库做文件 I/O；检查期间不抖动布局。
2. **完成文件关联**：`relinkCompletedFile { taskID, candidatePath, expectedArtifactRevision }`，由主进程文件选择入口组织调用，原生/Windows 引擎最终校验常规文件、任务状态和版本。返回新引用/任务快照，或稳定的 `candidateMissing | unreadable | notRegularFile | candidateChanged | taskChanged | persistenceFailed`。用户取消是独立正常结果，不发写请求、不报错。保存操作在同一任务锁内完成，候选在提交前重验，避免长时间选择器期间任务已重试的竞态。
3. **统一文件命令结果**：`{ ok: true } | { ok: false, reason, taskID, artifactRevision }`。`previewUnavailable` 与文件缺失分开；能确认文件存在但预览不支持时提供“打开文件”，系统接口不提供确切原因时不要自造分类。reveal 不再把“打开旧目录”当作“显示该文件”的成功；若保留打开目录，它是明确命名的不同动作。
4. **拖出失败事件**：带原拖拽请求标识、任务 ID 列表及各项原因。多选中有缺失时保留整组选区，明确“有 1 个文件不在原位置”，不静默只拖走部分文件，不把迟到错误关联到新的当前选中项。恢复入口可定位到缺失项，但不在拖拽期间弹系统选择器。

第 1、3 项应作为统一解析/交付层复用，避免 App、Inspector、卡片和快捷命令各自维护另一套缺失判断。preload 提供类型化 IPC；不要向 renderer 暴露任意数据库字段更新接口。关联路径属于本机信息，不进入远端日志或分析事件。

## 最小验收矩阵

所有测试使用隔离任务、临时目录与专用端口。Windows 必须在真实 Windows 目标上验收，macOS 上运行 Windows helper 测试不能代替平台结论。

| 场景 | 必须证明的结果 | 主要验证方式 |
| --- | --- | --- |
| 完成普通文件移动/重命名，原父目录仍在 | 空格、打开、显示位置得到明确缺失；“找到文件…”关联后动作使用新文件，任务不重复，原名与新位置可理解。 | 真实 Electron + 原生/Windows 引擎，临时目录；观察系统预览/显示行为。 |
| 同名不同内容、不同大小；旧任务无原身份；跨卷副本 | 不以名称/大小假称身份验证通过；明确手动关联；候选不被复制或改写。 | 引擎确定性测试 + 候选内容前后校验；跨卷使用隔离测试卷。 |
| 拒绝权限、离线卷、预览不支持 | 不误导为文件已移动；预览不支持仍能正常打开文件；失败提示不一直挡住内容。 | 文件系统错误注入及真实平台可实现的权限/预览案例。 |
| 取消选择、选目录/链接、候选选择后替换或消失 | 取消无副作用；非法/过期候选拒绝；旧引用仍在。 | 确定性候选验证与提交间屏障测试。 |
| 关联期间切换选中项、删除任务或重新下载 | 旧回执不覆盖新详情，不误开新选中项，不创建已删除任务；并发操作规则确定。 | 控制 RPC 回执与任务锁的真实 UI 边界测试。 |
| 持久化失败、重启、连续重新关联 | 写失败保留原引用；成功跨进程重启仍有效；版本校验拒绝旧提交。 | 存储故障注入 + 真实 Host/Windows 进程重启。 |
| 多选拖出，其中一项移走 | 指出缺失数量及对应任务，保留选择；关联后再次拖出包含完整选择；拖拽不唤起 NDM 接收遮罩。 | 真实系统拖拽到隔离接收应用/目录；检查完整路径集合与文件内容。 |
| 关联后重新下载、删除记录 | 外部关联文件及其同名旁侧文件不被清理；原有 segment/resume 所有权保护不变。 | 两套引擎生命周期测试，预置同名诱饵文件并逐一核验。 |
| 安装完成且 DMG 已移到废纸篓；媒体有旁侧产物 | 打开已安装应用仍可用；查找 DMG 不冒充查找应用；仅关联主文件不绑定同名字幕/转录。 | 安装收据 fixture、媒体主文件/旁侧文件 fixture + 详情交互检查。 |

现有 [fileDelivery.test.mjs](../../tests/fileDelivery.test.mjs) 只覆盖布尔/字符串结果到提示的映射；[fileDrag.test.mjs](../../tests/fileDrag.test.mjs) 覆盖路径集合与缺失拒绝；[qa-file-commands.mjs](../../scripts/qa-file-commands.mjs) 使用真实 Electron IPC，但引擎为隔离 fake，系统打开/显示动作被截获。它们适合扩展回归，**不能作为文件迁移恢复或真实系统预览已经验证的证据**。

## 建议实施顺序

先统一文件状态和交付错误，修正“原目录打开成功”等价于“文件已显示”的语义；随后完成单文件手动关联、独立引用与生命周期保护，最后接入拖拽失败的任务上下文。默认视图保持不变，先让一个缺失文件能被可靠找回并继续使用，再考虑自动发现或批量关联。
