# Composer：可恢复待下载清单审查

2026 年 9 月 12 日。下一轮方案，**尚未实现**。本轮只阅读当前源码与已有 QA，不修改产品行为，不读取真实剪贴板、私人链接或下载数据库，也没有执行新的退出、崩溃实验。

## 判断

最值得做的是让用户离开添加窗口后，仍能回来继续核对那一份清单。它应当像一个暂存的工作位置，不需要另加“草稿中心”、侧栏栏目或每次关闭时的确认弹窗。

但“保留清单”和“保证提交不重复”是两件事。当前界面在同一次打开期间已经能保留失败项、停止后留下剩余项，并排除本次已成功的 URL；这些保护都在内存里。若只把 `batchLinks` 写入本地存储，反而会把正在提交时已经成功的项一起恢复。

建议先做关闭与重开的清单保留，再为退出或崩溃后的未确认提交补上持久收据。未确认项在对账完成前不能成为普通的“重试”项。

## 已核对的现状

- [Composer.tsx](../../src/renderer/src/components/Composer.tsx) 的 `open` 变化会清空 `acceptedBatchURLs`；关闭分支清空链接、保存位置、连接数、失败提示和批量清单。组件仍由 [App.tsx](../../src/renderer/src/App.tsx) 常驻挂载，状态丢失来自主动重置，并非必须卸载组件。
- `submitBatch` 串行等待 `addFromUrl` 返回，成功 URL 放入 `acceptedBatchURLs`。`batchLinks` 直到停止或整批结束才替换为剩余项；处理中可见清单与真正未提交集合并不相同。
- `停止添加` 等待当前回执后才停止后续项；提交中的 Escape 被拦截。`destinationSession` 阻止旧回调修改新窗口，慢剪贴板、选目录和默认设置也已有会话边界。这些保护应保留。
- [composerBatch.ts](../../src/renderer/src/lib/composerBatch.ts) 只按当前清单和当前会话已接受集合排除相同 URL。普通文件的 `findDuplicate` 提示位于单链接解析路径；批量模式会跳过它。重复提示本身也允许用户明确再下一份，不能充当幂等合约。
- [store.ts](../../src/renderer/src/lib/store.ts) 的 `addFromUrl` 只有拿到 `reply.task` 才确认创建；否则抛错。[engine.ts](../../src/main/engine.ts) 的普通请求存在 20 秒超时和连接断开失败，但失败不能证明原生没有写入。
- macOS 的 [NDMHost/main.swift](../../native/Sources/NDMHost/main.swift) 在普通 `add` 中先调用 `manager.addURL` 插入任务，再启动并发送回执。[DownloadManager.swift](../../native/Sources/NDMEngine/DownloadManager.swift) 的普通 `addURL` 直接插入，未使用客户端幂等键。启动非排队错误或回执丢失，都可能出现“已存在任务，但界面认为添加失败”的路径。这是源码确认的风险，本轮未声称重新制造了网络丢包。

## 五个需要覆盖的场景

| 场景 | 当前结果与风险 | 最低干扰的目标行为 | 实现切点与验收 |
| --- | --- | --- | --- |
| **1. 准备十几条链接，选好目录，按 Escape 或点取消，稍后重开** | 全部重置。用户需要重新粘贴、移除不要的项和选目录；剪贴板若已经变化，原清单无法找回。 | 关闭保留有实际编辑的清单。下次普通“添加下载”回到原清单，不重新读剪贴板覆盖它。恢复时短暂说明“已恢复 12 项待添加链接”；“丢弃清单”放在当前窗口的次要位置，不进入左栏。保留草稿后，原“取消”应改为“关闭”，避免暗示已丢弃。 | 将草稿数据移出 `Composer` 的关闭重置分支；只重置焦点、加载和展示状态。受控粘贴三条，移除一条、选目录与连接数，关闭重开应恢复剩余两条和显式选择；零次 `add`。明确丢弃后重开为空。 |
| **2. 尚未提交，正常退出或 renderer 崩溃后重启** | 只有 React state/ref，没有恢复记录。窗口保护不能保住进程退出后的内容。 | 启动时不弹出添加窗口，也不自动下载。用户下次打开添加窗口才恢复清单。只保留一份当前批量清单，避免形成新的任务管理系统。 | 主进程管理独立草稿文件，保存已确认持久化的 revision。退出先完成待写入内容；用同一隔离目录分别正常退出、销毁 renderer、终止进程再打开，恢复清单但下载记录不增加。损坏、旧版本、写入失败必须分别验收。 |
| **3. 三项里已有一项成功，第二项失败；或点“停止添加”后关闭** | 同一次打开中，失败与未开始项能保留，成功项不会再次粘入。但关闭会同时丢失剩余清单和已接受集合。若只自动保存 UI 的 `batchLinks`，提交期间崩溃还会重新出现成功项。 | 恢复视图只列出尚需处理的项，成功项留在下载列表。恢复后的主按钮明确计数，例如“下载 2 项”；不把“处理了几项”当成“已创建几项”。用户之后明确建立新下载，仍允许下载同一 URL。 | 独立逐项状态记录；每个成功回执立即记录 task ID，再从可提交集合移出，不能只监听 `batchLinks` 变化。以可控回执验证成功/失败/未开始混合；关闭重开、重启后都只提交剩余项。断在每个回执与持久化边界，校验成功任务不重建。 |
| **4. 原生已插入任务，但启动报错、连接中断或回执尚未到达时退出** | 当前 catch 只留下 `failed: true`，重试再次 `add`。这是“结果不确定”，不能等同于“未创建”。URL 相同的历史任务也可能是用户有意再下一份，不能直接认领为本次成功。 | 恢复时把这一项标为“正在确认添加结果”。得到权威收据后，已创建的移至下载列表；明确未创建的才可提交。确认失败只给“重试确认”和“查看下载列表”，不能自动再创建。 | 为草稿项分配稳定操作键，并以请求内容摘要绑定；任务与收据在引擎中一起提交。相同键返回原 task ID，不再次启动、创建或覆盖文件。测试在插入后、发送回执前丢弃连接；重启后用同一键核对，任务计数仍为一。无收据能力的旧引擎保留未确认项，不伪装成可安全重试。 |
| **5. 有旧草稿，又从明确的新链接入口打开；或默认目录、链接有效期已经变化** | `[open, initialUrl]` 效果会重新准备链接；多链接入口可能替换原清单。恢复若遗漏 `folderEdited`、`connectionsEdited` 标记，迟到的默认值又会覆盖用户选择。签名链接和媒体格式也可能已经失效。 | 旧清单保持，明确传入的新链接先放在现有输入框，沿用“加入清单”和输入未处理时禁用整批提交的规则；不静默替换、合并或下载。自动剪贴板预填直接跳过。显式目录继续显示原选择；继承默认的项目使用当前默认。恢复不是重新授权。 | 在打开来源仲裁与草稿 hydration 中区分普通打开、明确传入链接和自动预填。恢复显式修改标记；重新检查目录可用性，媒体选择需重新解析后确认。测试晚到的设置/选择目录/剪贴板响应不能覆盖恢复状态，新链接不自动进入清单；全部使用合成域名和受控 IPC。 |

## 建议的保存合约

### 保存的是用户工作，不是界面缓存

第一版仅覆盖批量清单及它尚未加入清单的输入框内容。不要顺手持久化所有单视频解析状态、缩略图、可用空间、下载进度或完整分享口令。

最小记录包含：

- `version`、`draftID`、递增 `revision`、更新时间。
- 每项的稳定 `itemID`、准确 URL、用户 review 顺序、提交状态；签名查询参数不能为了“清理链接”而被改写。
- 当前输入框内容。它与已确认加入的项分开，恢复后仍需用户处理，不能被自动加入或提交。
- 保存位置和连接数分别标注 `inherit` 或 `explicit`。只记录真正显式选择的值，避免把当时默认值冻结成用户意图。
- 提交阶段才存在的操作键、内容摘要、已确认的 task ID，以及未确认状态。已接受集合只约束同一份草稿，不成为全库 URL 黑名单。

短错误提示应从状态生成，不持久化含原始请求、路径或服务器细节的整段错误。真实 URL、输入内容和目录不得进入日志、诊断导出或审查截图。

### 清楚划分三个承诺

1. **仍在编辑**：以小延迟合并保存。手动粘贴、编辑、移除或明确导入才使清单成为可保存草稿；仅自动读取到剪贴板内容、用户什么也没做就关闭，不应悄悄建立持久记录。
2. **准备发出创建请求**：先持久化这一项的操作键和固定请求参数，再发送。此刻还不能删除草稿项或标记成功。
3. **收到确认**：持久记录实际 task ID，然后从“待添加”中移出。拒绝与结果不确定要分别记录。所有项都已确认后，清除草稿；成功任务完全归下载库管理。

崩溃发生在“收到成功回执，但成功状态尚未落盘”之间时，旧记录仍会显示未确认。因此只靠主进程草稿文件无法保证不重复；必须能再次向引擎查询同一个操作键。进程内自增 RPC `id` 不是这个键。

macOS 已有 [Relay 收据事务](../../native/Sources/NDMCore/Storage/DownloadStore.swift) 可参考原子提交方式，但不能直接复用其命名空间或把 URL 当 request ID。普通 `add` 的“创建成功”和“随后开始下载是否成功”也应分开表达，已插入的任务不能因为启动失败而被当作从未创建。Windows 的 [windowsEngine.ts](../../src/main/windows/windowsEngine.ts) 需要同等合约；不能只在 macOS 做去重后就跨平台承诺安全恢复。

### 持久化与失败边界

- 草稿由主进程单一写入者维护，使用应用当前数据目录和隔离目录配置；不写入下载文件夹，不混进任务表，不改变分段存储或清理所有权。
- 写入串行化，并用 revision 拒绝迟到保存；临时文件写入后原子替换。可参考 [temporaryBandwidth.ts](../../src/main/temporaryBandwidth.ts) 的文件提交结构。丢弃也需推进版本，防止旧回调重新创建已丢弃草稿。
- 含完整 URL 的载荷应使用系统支持的受保护本地存储。当前主进程尚无草稿加密实现，不能把这项当作已经解决；若不可用，不静默降级为保存含凭据链接的明文。权限、解密失败和移动数据目录须单独验证。
- 不持久化 Cookie、Authorization、自定义登录会话或 URL 中的明文账号密码。需要认证时重新走现有浏览器/凭据流程；恢复 URL 不代表恢复授权。
- 正常关闭无需询问。只有确实无法持久化且退出会丢失内容时，才保留编辑状态并解释“草稿未能保存”；不得显示“已保留”。保存失败不能删除上一份有效 revision。
- 不默认设置短期自动删除。完整成功或用户明确丢弃才清除内容；文件损坏或新版本无法读取时保留原文件，显示可恢复说明，不因解析失败立刻写入空草稿覆盖它。

## 已有 QA 能证明什么

[qa-composer-batch-review.mjs](../../scripts/qa-composer-batch-review.mjs) 已定义受控 IPC 场景：粘贴不提交、去重和移除、同一次打开中的混合成功失败、已成功 URL 不重新加入、停止后继续、挂起请求期间 Escape、慢剪贴板不覆盖新输入。它随后重开一个新窗口准备下一批，**没有断言上一次未提交清单被恢复**。

[qa-composer-destination.mjs](../../scripts/qa-composer-destination.mjs) 覆盖目录和连接数不被迟到默认覆盖，以及旧目录选择不污染下一次打开；[composerBatch.test.mjs](../../tests/composerBatch.test.mjs) 覆盖内存集合去重。它们不证明进程崩溃恢复、提交收据持久性、故障后恰好创建一次或跨平台一致性。

下一轮新增验证应使用启动前就替换好的合成剪贴板与测试域名，不先读真实剪贴板再覆盖。恢复测试必须重新启动同一个隔离配置，而非仅查看当前 React state；提交故障测试必须检查引擎实际任务数量、task ID 和真实回执，不能仅观察窗口消失。

## 下一轮建议切分

**先做可感知且边界清晰的保留工作位置**：提取 draft reducer/store，保留纯未提交清单和选项，关闭/重开恢复，明确丢弃，处理新链接入口仲裁。验收不能增加默认界面高度，也不能新增侧栏入口。

**再做跨退出的逐项提交恢复**：主进程持久文件、操作键与引擎收据、未确认项对账，覆盖普通文件两端实现。可先只承诺已保存的纯待提交内容；在收据机制完成前，对正在提交或回执不明的项保持“待确认”，不要给出“所有失败项都可直接重试”的承诺。

本轮文档不要求重做媒体解析、合集、任务数据库、浏览器接管或多份草稿管理。以上五个场景闭环后，再判断单链接/媒体选项草稿是否有足够收益。
